# 设计说明

## 1. 问题理解与系统边界

业务方真正需要的是把“缓慢、不稳定、协议各异的外部通知”从业务主流程中移走，而不是得到一个通用 API 网关。

### 第一版假设

题目没有提供峰值流量、最长允许延迟、供应商幂等能力或部署环境，因此不虚构 QPS / SLA。
本版按“单机、一个可信内部租户、多业务系统、小体积文本通知、无严格顺序要求”实现。这些是明确的设计假设，不是对所有企业场景都适用的结论。
如果实际要求多机可用或分钟内大批量送达，应先重新确认容量和存储方案，而不是直接套用本版默认值。

### 本系统解决

1. 接收已构造好的 HTTP 请求，校验并持久化后快速确认。
2. 保存投递状态，异步执行，不让业务调用方等待供应商。
3. 管理短暂失败、有限自动重试、Worker 中断后的恢复。
4. 保留死信和尝试历史，支持排查与人工重投。
5. 防止上游重试创建多个相同任务，提供最小访问控制与目标约束。

### 明确不解决

| 不解决的问题 | 原因与责任归属 |
| --- | --- |
| 业务事件与入队跨系统事务 | 服务不知道用户注册/订单事务；业务方需要自己的 transactional outbox，并重试提交直到收到 202 |
| 供应商协议转换、动态签名、OAuth 刷新 | 与每个供应商强耦合；MVP 由业务方构造，未来有重复需求再抽取适配器 |
| 供应商内部业务成功 | HTTP 200 也可能包含业务错误，HTTP 202 可能只是供应商已接收；本版仅以 2xx 判定 HTTP 投递成功 |
| Exactly-once 业务效果 | 本地状态与外部 HTTP 副作用无法做原子提交，需要供应商幂等配合 |
| 严格顺序、优先级、任务取消、指定时间投递 | 题目没有要求，不增加调度复杂度 |
| 无限自动重试、所有故障下必达 | 错误配置或长期故障不能无限消耗资源；需要人工介入与补偿 |
| 多租户权限、分租户配额、公开互联网服务 | 只面向一个可信内部租户，多个业务系统共享认证与幂等命名空间 |
| 任意二进制、文件上传、超大消息 | 第一版聚焦小体积文本 HTTP 通知 |
| 多机高可用、跨地域容灾 | 本版明确是单机持久化方案；不冒称 SQLite 等于高可用 |

## 2. 整体架构

```text
业务系统 / 上游 Outbox
       |
       | POST + Idempotency-Key
       v
FastAPI 进程 ---- 事务提交后返回 202
       |
       v
SQLite（本地持久盘，WAL，synchronous=FULL）
  notifications：原请求、状态、时间、租约、幂等指纹
  attempts：每次领取/投递的审计记录
       ^
       | 原子领取、写回结果
       |
独立 Worker 进程 ---- HTTP(S) ----> 供应商
       |
       +---- 重试到期重新领取 / 进入死信
```

接收和调度使用同一个数据库事务边界，不另行“写数据库后发队列消息”，避免数据库与消息队列双写问题。
网络 I/O 不在数据库事务内；Worker 等待供应商时不会持有写锁。

主要模块：

- [API](../notify_service/api.py)：鉴权、HTTP 契约、提交/查询/重投。
- [Store](../notify_service/store.py)：事务、原子领取、租约校验、历史记录。
- [Worker](../notify_service/worker.py)：投递、HTTP 分类、总时限、重试调度。
- [配置](../notify_service/config.py)与[策略](../notify_service/policy.py)：启动校验、精确 origin 和 Header 规则。

## 3. 状态与原子性

```text
pending --到期领取--> in_flight --2xx--> succeeded
   ^                       |
   |                       +--可重试且未耗尽--> pending（设置 next_attempt_at）
   |                       +--永久失败/耗尽----> dead
   |                       +--租约到期--------> 再领取，或耗尽后 dead
   |
   +----------------------- dead --人工 redrive
```

### 接收幂等

- 调用方提供稳定事件 key；数据库唯一约束为最终保护。
- `BEGIN IMMEDIATE` 中读取 key、比较请求指纹、插入记录，提交之后才能返回 202。
- 同 key 不同内容返回 409，防止调用方误用幂等键。
- 客户端超时可能发生在事务提交后：业务方必须用原 key 重试，不能随意生成新 key。
- 任务没有自动删除；未来清理时必须同步设计幂等保留窗口，避免旧事件重新执行。

### 领取和租约

- `BEGIN IMMEDIATE` 串行化领取事务；多个 Worker 进程共享同一文件时，不会同时领取仍在有效租约内的任务。
- 领取时先增加计数、生成随机 token、设置租约、插入尝试记录并提交，然后才发 HTTP 请求。
- 领取也计入尝试预算：即使进程在发 HTTP 之前崩溃，也不能无限崩溃/重领。
- 写回必须同时满足 `id + in_flight + claim_token + lease_until > now`。
- 领取和结果写回都在取得写锁后采样时钟，避免锁等待消耗新租约，或使用等待前的旧时间放行已过期的结果。
- 租约过期后，之前的尝试标为 `unknown / lease_expired`，因为无法判断请求是否已经到达供应商。
- 旧 Worker 不能覆盖新 Worker 的状态；但 token **只能隔离本地写回，不能撤销已经发出的 HTTP 副作用**。
- 最后一次尝试崩溃后进入死信，仍然标记结果未知，而不是伪造供应商失败或成功。

Worker 默认串行，没有心跳续租。单次请求总时限为 10 秒，租约 30 秒；配置要求至少预留 5 秒。
这是固定短任务的简化取舍。如果将来需要长任务或高并发，应设计续租、调度延迟预算和更严格的时间处理。
调度时间存储为 Unix 时间，要求主机时钟稳定；系统挂起或时钟跳变可能导致重复或延迟，不能用租约消除该风险。

### 写回与崩溃

任务状态和尝试记录在同一个事务中更新。落库失败不会报告成功；Worker 遇到未处理的数据库操作错误退出，由运维发现并重启，任务通过租约恢复。

### 故障窗口：到底会不会丢、会不会重

| 故障发生位置 | 恢复方式 | 剩余风险 / 验证依据 |
| --- | --- | --- |
| 业务事务完成，但调用本服务之前退出 | 业务方 outbox 重放提交 | 超出本服务边界 |
| 入队已提交，202 响应丢失 | 同 key 重试返回同一 ID | [API 幂等测试](../tests/test_api.py) |
| 入队后 API / Worker 退出 | 重启后从同一持久化文件继续 | [真实进程重启测试](../tests/test_end_to_end.py) |
| 领取已提交，HTTP 发出前退出 | 租约到期后再领取，原尝试为 unknown | 消耗一次预算；[租约恢复测试](../tests/test_store.py) |
| 供应商已收到，但响应 / 本地确认未完成 | 租约或失败重试 | 可能重复；[真实投递中强杀测试](../tests/test_end_to_end.py)、[成功后未确认模拟](../tests/test_worker.py) |
| 本地 succeeded 已提交后退出 | 不再领取该任务 | [终态不重领测试](../tests/test_store.py) |
| 等写锁时租约到期 | 取得锁后校验，拒绝旧结果 | [锁等待回归测试](../tests/test_store.py) |
| 历史请求不再通过当前校验 | 隔离到 dead，记录 invalid_stored_request，继续其他任务 | 避免一个旧记录阻塞整个队列；[回归测试](../tests/test_store.py) |
| 本地磁盘永久损坏 | 依赖备份恢复 / 上游补偿 | 单机 MVP 无法自行保证不丢 |

## 4. 投递语义与失败策略

### 选择：允许重复的重投机制，有预算和死信边界

对于已接收的任务，在本地数据仍完整、Worker 能恢复运行且自动预算未耗尽的前提下，会反复尝试投递。
**允许重复，不保证恰好一次；最多 6 次尝试后保留死信，因此不是无条件的最终必达保证。**
这是沿用 at-least-once 的重投处理方式，但不声称“每个接收任务最终至少成功一次”。如果连续在发送前崩溃耗尽预算，甚至可能一次 HTTP 都没有真正发出；可恢复的是任务记录和人工处置能力。

典型重复场景：

1. 供应商已提交操作，但响应丢失。
2. 供应商返回 2xx，Worker 在写本地成功状态之前退出。
3. 租约到期、进程恢复或人工重投一个结果不确定的任务。

措施：

- 每次携带稳定 `X-Notification-Id`。
- 如果供应商支持幂等键，业务方在出站 Header 中提供供应商要求的 key。
- 供应商不支持幂等时，重复库存扣减/计费等风险仍存在；业务方必须使用自然业务唯一键、对账或补偿，不能仅依赖本服务。

### HTTP 判定表

| 结果 | 策略 |
| --- | --- |
| 任意 2xx | 标记 `succeeded`，不消费响应 Body |
| 408、425、429、5xx | 有剩余预算则重试，否则死信 |
| 网络连接错误、TLS/协议错误、读写超时、总时限耗尽 | 作为可重试传输失败，受相同预算限制 |
| 其他 4xx | 直接死信，通常需要修复鉴权/请求参数 |
| 3xx | 不跟随，直接死信，避免改变请求目的地或泄露认证 |
| 目标不再位于当前配置的白名单 | 不发 HTTP，直接死信 |

对 TLS 配置错误等通常长期存在的问题也只做有限重试，避免为了细分传输错误添加复杂分类。需要更细策略时按供应商配置演进。

### 退避

第 n 次失败后的基础上界：

```text
ceiling = min(3600 秒, 30 秒 × 2^(n-1))
delay = Uniform(ceiling / 2, ceiling)
```

默认最多 6 次，包含首次，因此只有五段等待：

| 失败次数 n | 下一次尝试前的等待范围 |
| --- | --- |
| 1 | 15～30 秒 |
| 2 | 30～60 秒 |
| 3 | 60～120 秒 |
| 4 | 120～240 秒 |
| 5 | 240～480 秒 |

累计等待为 **465～930 秒（7 分 45 秒～15 分 30 秒）**，还要加上请求耗时和队列排队。
这给分钟级短暂故障留出恢复机会，但不会自动覆盖小时级故障。6 次、30 秒基数是本次确认的第一版取舍，不是来自生产统计；上线应根据业务时效、供应商恢复时间和告警响应时间调参。
原先 2 秒基数会在约 31～62 秒等待后耗尽预算，复核后改为仅用于演示，避免将“演示跑得快”误当成合适的故障策略。[等待窗口测试](../tests/test_worker.py)验证了上下界。

支持 `Retry-After` 的秒数和 HTTP 日期，取基础退避与供应商建议的较大值，供应商建议最多等 3600 秒。无效值记录警告并使用基础退避。
这是有意的运维上限，不是对供应商任意等待要求的无条件服从。极端长维护窗口应暂停相关流量或转人工处理。
截止时间落库，Worker 通过轮询挑选到期任务，不会在一次重试的等待期间阻塞其他就绪任务。

### 长期不可用和人工恢复

达到预算进入 `dead`，不删除，原请求和尝试历史保留。
操作人员查看状态、HTTP 码和错误类型，确认供应商恢复或修复配置后，再执行 `redrive`。
重投保留稳定通知 ID，重置本轮预算；永久 400 的请求原样重投仍会失败。
本版不自带告警平台或自动死信回放，值班人员需要关注死信和积压。不能把“有死信表”当作“已经完成运维闭环”。
人工重投的响应不确定时，应先查当前状态和历史；本版没有为重投操作本身提供独立幂等键，不能把入口提交的自动重试规则直接套到运维重投上。

## 5. 为什么使用 SQLite，而不引入消息中间件

题目没有给吞吐量或高可用指标，应优先让可靠性逻辑易于验证，而不是预置分布式系统。

- SQLite 随 Python 提供，零额外服务，适合单机低流量 MVP。
- 事务同时管理任务、幂等和尝试记录，避免多种存储之间的一致性问题。
- WAL 允许读写更好地并行，`synchronous=FULL` 增强提交持久性，但最终仍依赖磁盘、文件系统与硬件保证。
- 缺点是单写者、本机故障域、无自动副本切换；多 Worker 不等于多机扩展。
- **不要把数据库文件放在网络共享盘上供多机并发访问。**

不用 SQLite 时，第一替代是 PostgreSQL 任务表，以事务和 `FOR UPDATE SKIP LOCKED` 领取任务；接收契约和状态机基本保持不变。
只有确认数据库任务表无法满足峰值、隔离或扩展需求时，再评估 RabbitMQ 等队列。
若同时使用业务状态库和队列，必须用 outbox/CDC 等方式处理双写，不以“使用消息队列”替代可靠性分析。

另外两个有意保留的简单选择：

- **直接 SQL，而不是 ORM + 通用仓储层**：只有两张表，可靠性重点在事务和条件更新。将这些行为直接写出来更便于审查；数据模型复杂后再考虑抽象和迁移框架。
- **独立串行 Worker，而不是 API 内后台任务或复杂调度平台**：可靠性由数据库承载，生命周期与 API 解耦；串行吞吐和供应商相互影响是已知代价，后续有指标再做有界并发。

## 6. 安全与运行约束

- 入口 API Key 至少 32 个非空白可打印 ASCII 字符，采用常量时间比较。它是内部共享凭据，不是多租户授权系统。
- 生产入口需要 TLS、网关鉴权与请求速率/连接时限限制；请求体大小限制不能替代网关抗滥用能力。
- 白名单精确匹配 scheme、host、port，配置权归管理员；普通业务方不能动态扩大白名单。
- 禁止 URL 用户名/密码、fragment、反斜杠以及手工覆盖危险 Header；HTTPS 使用正常证书校验。
- 禁止跟随重定向、不读取环境代理、不跨通知沿用 Cookie。
- 白名单不等于完整 SSRF 防御：本版不实现解析 IP 固定或 DNS 重绑定防护，要求管理员控制可信域名/DNS，并用出站防火墙阻断非预期内网和云元数据访问。回环 origin 仅用于本地演示。
- 请求中的 Token、Body、URL 查询参数会以明文保存在 SQLite。必须使用专用运行账户、最小文件权限和磁盘/备份加密；本版不提供应用层加密或密钥轮转。
- 业务日志只记录通知 ID、尝试次数、状态码和错误类别，不记录出站 URL、凭据和 Body；Worker 降低 HTTPX 默认 URL 日志级别。
- 配置变化需要重启进程；旧任务的请求和认证 Header 不会自动刷新，过期签名可能需要重新提交正确请求。

## 7. 运维与后续演进

本版只提供日志、状态查询和数据库可读性检查。生产至少需要：

1. **进程守护**：分别管理 API / Worker，失败显式告警和重启；仅 API 健康不代表能投递。
2. **监控指标**：pending 数量、最老等待年龄、dead 增速、成功率、延迟、重试次数、过期租约数、磁盘剩余量。
3. **备份恢复**：停机备份，或使用 SQLite backup API；不能只拷贝活动中的主文件而忽略 WAL。定期演练恢复。
4. **容量与保留策略**：本版不自动清理，保留历史便于作业验证，但会持续占用磁盘。上线前定义历史保留期、幂等窗口与容量告警。
5. **故障处理**：磁盘满/数据库不可用时接收失败，上游使用同一 key 重试；单机存储永久损坏会丢数据，不能靠本版自动补救。

按实际瓶颈演进，而不是一次全部加入：

| 触发条件 | 下一步 |
| --- | --- |
| 单 Worker 等待外部 I/O 导致队列年龄持续超过业务 SLO | 加有界并发/少量本机 Worker，验证数据库锁等待和供应商限额 |
| 不同供应商故障互相拖累 | 按供应商限速、隔离并发、熔断；先取得实际失败率和限流规则 |
| 单写者锁等待或多机高可用成为明确需求 | 迁移 PostgreSQL、引入迁移管理和备份副本 |
| 高峰积压/消费扩展已超出任务表能力 | 引入消息队列，明确定义确认、重复、延迟重试和 outbox 一致性 |
| 供应商适配重复、认证过期频繁 | 增加独立供应商适配器、运行时签名、凭据引用 |
| 多团队共享导致权限或容量冲突 | 分租户密钥、幂等命名空间、配额、审计权限 |
| 历史体积或人工排障复杂度增加 | 归档、全量分页、检索与运维界面 |

不提供未经压测的 QPS 数字，也不承诺当前架构能达到未定义的生产 SLO。
