# AI 使用说明

本项目使用 VS Code 中运行于 Copilot CLI runtime 的 AI 助手完成分析、实现与验证。AI 参与程度较高：代码、测试和文档主要由 AI 生成并迭代，作者负责选择与确认关键方案。以下区分实际人工确认、AI 提议和验证证据，不把 AI 的工作归为人工独立完成。

## 1. AI 在哪些关键地方提供帮助

| 环节 | 具体帮助 |
| --- | --- |
| 拆解需求 | 区分“业务事件产生”“本服务接收成功”“HTTP 投递成功”“供应商业务成功”四个边界 |
| 设计可靠性 | 推导幂等入队、持久化领取、租约恢复、旧 token 隔离，以及外部成功但本地未确认的重复窗口 |
| 实现 MVP | 编写 FastAPI / SQLite / HTTPX 模块，完成失败分类、退避、死信与人工重投 |
| 验证方案 | 编写并发与状态机测试，启动真实 API / Worker / HTTP 供应商，验证重启和投递中断 |
| 复核与修正 | 用失败回归测试找出锁等待时间戳、Header 可发送性、Retry-After 解析问题，再修改实现 |

## 2. 哪些建议没有采纳

### 实际交互中没有选择的方案

| AI 给出的选项 | 最终选择及取舍 |
| --- | --- |
| Go + SQLite，或 Java + Spring Boot + PostgreSQL | 选择 Python + FastAPI + SQLite：优先低依赖、可读性和本地复现，不把语言或部署复杂度当作评分目标 |
| 外部长期不可用时无限自动重试 | 选择最多 6 次后转死信：重试有资源预算，长期故障由排查、重投和补偿处理 |
| 初版实现沿用 2 秒退避基数 | 复核累计等待只有约 31～62 秒后，确认改为正常基数 30 秒，2 秒仅留作演示 |

这些不是“AI 一定错了”：Go、PostgreSQL、无限重试都有适用场景，只是不适合本次确定的第一版边界。

### 方案评估中认为过度、没有实施的设计

以下是 AI 评估后排除的设计，没有虚构为作者曾在对话中逐条否决：

- **Kafka / RabbitMQ + Redis + 分布式调度**：题目没有吞吐或多机高可用指标。先用一个事务存储把不丢进程内任务、重复与恢复讲清楚。
- **供应商插件、工作流引擎、管理后台**：通用 HTTP 请求已经覆盖 MVP；新增平台能力反而会掩盖可靠性核心。
- **用协调层包装 exactly-once 承诺**：任意 HTTP 供应商不能加入本地事务，协调层无法消除外部副作用与本地确认之间的窗口。
- **提前实现严格顺序、多租户配额、自动死信回放**：缺少业务依据，作为明确的后续演进而非默认实现。

## 3. 哪些关键决定由作者确认，以及为什么

以下决定在实际交互中由作者明确选择：

1. **Python + FastAPI + SQLite**：从 AI 提供的技术栈中选择，优先少依赖和可验证的持久化机制；不为 MVP 额外搭建数据库服务。
2. **有限重试 + 死信 + 人工重投**：选定 6 次尝试上限，接受长期故障需要人工介入，而不是宣称永久自动必达。
3. **区分正常参数与演示参数**：看到 2 秒基数对应的真实等待窗口后，确认正常基数改为 30 秒，使自动尝试覆盖分钟级短暂故障；演示仍使用短间隔。
4. **仓库名 `rc_jiangzhang`**：按作业要求确认提交名称。

这些是已确认选项及其取舍含义。SQL 写法、租约 token、HTTP 分类等更细的实现由 AI 提出，未冒称作者亲自逐行编写或独立设计。

## 4. 如何判断 AI 输出是否可信

不以“代码看起来完整”作为验收，而是将可靠性承诺变成能失败的测试。本次复核留下了以下实际记录：

| 初稿中的问题 | 判断与修正 | 证据 |
| --- | --- | --- |
| 获取数据库写锁前读取时钟 | 等锁会缩短新租约，或让过期结果使用旧时间回写；改为拿到锁后读取，Worker 不再传入旧时间 | [Store 回归测试](../tests/test_store.py)，先复现失败再修正 |
| Header 值带首尾空格仍返回 202 | HTTP 客户端实际拒绝发送；提前校验，不浪费重试预算 | [API 回归测试](../tests/test_api.py) |
| `Retry-After: 00000000001` 被当作超长等待 | 长度防护不能把数值 1 秒误判为 1 小时；先去前导零再判断 | [Worker 回归测试](../tests/test_worker.py) |
| 强化校验可能让历史旧请求阻塞领取 | 无法解析的历史请求隔离到死信，保留错误类别并继续后续任务 | [旧请求隔离测试](../tests/test_store.py) |
| 只有空闲进程重启不足以证明恢复能力 | 增加供应商已收到请求时强杀 Worker，真实等待租约后重投 | [端到端测试](../tests/test_end_to_end.py) |

这些测试与修正也由 AI 执行，可作为作者亲自复现和检查的材料；它们不等于生产可靠性认证。

## 5. 验证范围

运行方式见 [README](../README.md)。本地证据覆盖数据库状态机、并发、HTTP 分类和真实进程故障恢复。
没有声称已经做过生产压测、真实供应商联调、多机容灾或线上稳定性验证。提交前应亲自运行一键验收，能解释为什么可能重复、为什么会进入死信，以及出现什么指标后才值得引入消息队列。
